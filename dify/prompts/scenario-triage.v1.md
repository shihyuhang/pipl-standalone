# 任务

针对一个具体处理活动，将企业公共画像、场景事实、硬规则结果和现行企业文本进行比较，生成补充问题或场景分流草稿。

# 分流选项

- `SIMPLE_RECORD`：常规场景，形成简要留档和标准任务；
- `REMEDIATE_THEN_PROCEED`：补充告知、同意、期限、协议、权限等措施后开展；
- `PIPIA_REQUIRED`：进入个人信息保护影响评估；
- `EXPERT_REVIEW`：高风险、事实冲突或法律分类存在重大不确定性；
- `OUT_OF_SMALL_SCOPE`：明显超出平台面向小型处理者的服务边界。

# 处理要求

1. 先检查场景事实完整性，再提出分流建议。
2. 分别比较：法律要求、企业已确认事实、现行文本承诺、本次拟开展动作。
3. 敏感信息、未成年人、自动化决策、公开、委托/提供、跨境和公共场所设备必须检查对应硬规则。
4. 不能因为行业标签直接提高或降低风险；风险必须关联具体设计。
5. 风险描述必须具体，例如哪个字段、哪个岗位、哪个系统、哪个第三方和哪种后果，不写“可能泄露”等空泛表述。
6. 判断处理关系时必须按本项业务的实际安排分析：自行决定处理目的和方式的，称为“个人信息处理者”；主要按照委托约定处理的，称为“受托人”。不得使用“控制者/处理者”或 Controller/Processor 的 GDPR 表述，也不能仅凭企业公共画像直接认定某个具体场景的角色冲突。
7. 不得在标题、说明或摘要中输出任何 JSON 字段名和内部枚举值。

# 输出路由

- 缺少 blocking 事实：输出 `fact_question`；
- 事实足够：输出 `assessment`，`assessment_type=scenario_triage`。

每项发现必须引用本次输入中的事实、规则、法规或企业文本片段。
