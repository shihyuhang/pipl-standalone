## 二、检测方法

直接对 SQLite 隔离库执行产物级核查，覆盖维度：

1. **留白检测**：扫描 `待结合实际业务补充` / `待补充` / `待确认` / `待逐项确认` / `【待…】` / 下划线填空等占位符
2. **标题代号检测**：正则匹配 `单位·(privacy_notice|sensitive_consent|…)` 内部代号
3. **单位名匹配**：正文是否含建档快照中的单位全称
4. **串扰检测**：词边界正则匹配是否混入其他 9 家机构名
5. **章节-事实匹配**：按 `facts_snapshot_json` 中的 `minorsPossible` / `crossBorder` 核对正文对应章节
6. **差异化检测**：同类型材料 content_hash 去重 + 抽样人工比对

## 三、关键发现

### 发现 1（高）：15 份 PIPL 强制项留白材料已发布

| 材料类型 | 留白数量 | 缺失的强制告知项 | 法条 |
|---|---|---|---|
| 敏感个人信息单独同意书 | 9/9 | 处理必要性、对个人权益的影响、保护措施 | PIPL 第 30 条 |
| 个人信息出境同意书 | 6/6 | 境外接收方名称和联系方式 | PIPL 第 39 条 |

**典型留白原文**（成都康众 sensitive_consent）：

```
- 处理必要性：待结合实际业务补充
- 对个人权益的影响：待补充
- 保护措施：访问权限、加密或去标识化、保存期限控制及其他实际措施待确认
```

**根因**：这批材料由 e2e 脚本于 **2026-08-18 上午**生成并发布，而 P0-4/P0-5 拦截校验是**当天下午 P0 批次才加入 `publishDocumentVersion`** 的。拦截机制上线晚于数据生成，属预期内的历史遗留，**非校验逻辑缺陷**。

### 发现 2（已验证）：P0-4/P0-5 拦截机制实测生效

在干净库上对 `publishDocumentVersion` 做了 7 项单元级实测：

| 用例 | 期望 | 实际 |
|---|---|---|
| 敏感同意书含"待结合实际业务补充" | 拦截 | ✅ SENSITIVE_FIELDS_INCOMPLETE |
| 敏感同意书含"待补充" | 拦截 | ✅ SENSITIVE_FIELDS_INCOMPLETE |
| 敏感同意书含"待确认" | 拦截 | ✅ SENSITIVE_FIELDS_INCOMPLETE |
| 敏感同意书完整 | 放行 | ✅ 正常发布 |
| 出境同意书含"待逐项确认" | 拦截 | ✅ CROSS_BORDER_RECIPIENT_INCOMPLETE |
| 出境同意书完整 | 放行 | ✅ 正常发布 |
| 普通隐私政策 | 放行（不受专项校验影响） | ✅ 正常发布 |

**结论**：拦截机制本身正确。**今后新生成的留白材料无法发布**。历史 15 份需在数据层面处理（见建议）。

### 发现 3（低/设计如此）：内容"雷同"是测试重复，非系统缺陷

同类型材料 content_hash 去重显示"唯一内容 7/21"等，初看像雷同。深入核查后确认：

- **102 份 = 34 个唯一（机构×类型）组合 × 3 次重复生成**——e2e 脚本对每家机构重复建了 3 次同样材料
- 抽样人工比对两家机构的隐私政策（杭州唇齿 vs 上海晨曦）：**结构骨架相同，但业务名、人数、自动化决策、未成年人、境外、对应章节内容全部正确差异化**

这是确定性模板的正常表现：骨架统一保证合规要素齐全，事实字段按输入填充。**符合预期，无需处理。**

### 发现 4（已纠正）：命名"内部代号"是测试脚本行为，非系统缺陷

初查时认为材料标题 `单位·privacy_notice` 等英文代号是系统默认。**深入核查后纠正**：

- 系统 `materialCatalog[].name` 每种材料都有正式中文名（如 `sensitive_consent` → "敏感个人信息单独同意书"），创建向导 `setName(next.name)` 用的就是中文名。**系统默认名本来就是中文。**
- 测试库里的 `单位·英文代号` 来自 `tmp/e2e-tenants.mjs` 第 236 行 `name: ${t.name.slice(0,4)}·${m.type}`——e2e 测试脚本自取的代号，非系统行为。

**结论**：命名问题不存在，无需修订。此条为误报。
